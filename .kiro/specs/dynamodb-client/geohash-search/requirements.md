# 要件定義書: GeoHash検索機能

## はじめに

本機能は、開催地の位置情報検索を効率化するため、GeoHashを用いた空間インデックスを実装します。これにより、ユーザーの現在地から近い開催地を高速に検索できるようになります。

## 用語集

- **GeoHash**: 緯度・経度を1次元の文字列に変換するエンコード方式
- **アプリ**: モバイルアプリケーション（Flutter）
- **Records_API**: Records Lambda（BFF）
- **DynamoDB_Client**: DynamoDB Client API
- **開催地**: ラジオ体操の開催場所
- **位置情報**: 緯度・経度のペア
- **精度**: GeoHashの精度（文字列長）
- **候補**: 検索候補となる開催地

## 要件

### 要件1: GeoHashベース開催地検索

**ユーザーストーリー:** ユーザーとして、近くの開催地を効率的に見つけたい。そうすれば、自分の近くの運動場所をすぐに発見できる。

#### 受け入れ基準

1. アプリが位置情報と取得件数をパラメータに開催地検索をリクエストしたとき、Records_APIは距離の近い順に開催地の配列を返却すること
2. Records_APIが検索リクエストを受け取ったとき、提供された位置情報からGeoHashを計算すること
3. 開催地を検索するとき、Records_APIはGeoHash前方一致を使用して候補を検索すること
4. 候補が見つかったとき、Records_APIは実際の距離（大円距離）でソートすること
5. 要求された件数の開催地が見つからなかったとき、Records_APIはGeoHash前方一致の条件を緩和して再試行すること

### 要件2: GeoHash自動保存

**ユーザーストーリー:** システム管理者として、開催地の位置情報が自動的にインデックス化されることを望む。そうすれば、検索が高速で効率的になる。

#### 受け入れ基準

1. 開催地が作成または更新されたとき、DynamoDB_ClientはGeoHash値を8文字精度（±19m）で計算して保存すること
2. 開催地が保存されるとき、DynamoDB_Clientは位置情報（緯度、経度）とGeoHash値の両方を保存すること
3. GeoHashフィールドが保存されるとき、@exabugs/dynamodb-clientはGeoHashフィールドに自動的にシャドウインデックスを作成すること
4. 開催地の位置情報が更新されたとき、GeoHash値は8文字精度で再計算され更新されること
5. シャドウインデックスに保存されるGeoHashは、検索開始精度（6文字）より高い精度で保存されること

### 要件3: 隣接ブロック検索による完全性保証

**ユーザーストーリー:** 開発者として、検索アルゴリズムが境界をまたぐ近くの開催地を見逃さないことを望む。そうすれば、ユーザーは常に関連する結果を見ることができる。

#### 受け入れ基準

1. 開催地を検索するとき、Records_APIは対象地点のGeoHashと隣接する8方向のGeoHash（合計9ブロック）を検索対象とすること
2. 隣接GeoHashを取得するとき、Records_APIは上、下、左、右、左上、右上、左下、右下の8方向を計算すること
3. 日付変更線や極付近の境界をまたぐとき、Records_APIは適切に隣接GeoHashを計算すること
4. 9ブロックから候補が取得されたとき、Records_APIは重複を排除すること
5. 候補が見つかったとき、Records_APIは実際の距離（大円距離）でソートすること

### 要件4: 段階的精度緩和検索

**ユーザーストーリー:** 開発者として、検索範囲を段階的に広げることで、十分な候補を取得したい。そうすれば、ユーザーは常に適切な数の結果を見ることができる。

#### 受け入れ基準

1. 9ブロック検索で十分な候補が見つからなかったとき、Records_APIはGeoHash精度を1文字減らして再検索すること
2. 精度を緩和するとき、Records_APIは新しい精度で再度9ブロック検索を実行すること
3. 精度が最小閾値（4文字）に達したとき、Records_APIは精度の緩和を停止すること
4. 候補が要求された件数の3倍を超えたとき、Records_APIは検索を停止すること
5. 最大反復回数（5回）に達したとき、Records_APIは検索を停止すること

### 要件5: 距離計算の正確性

**ユーザーストーリー:** ユーザーとして、実際の距離でソートされた開催地を見たい。そうすれば、検索結果を信頼できる。

#### 受け入れ基準

1. 距離を計算するとき、Records_APIは大円距離にHaversine公式を使用すること
2. 開催地をソートするとき、Records_APIはGeoHashの類似性ではなく、計算された距離を使用すること
3. 結果を返却するとき、Records_APIは各開催地の計算された距離を含めること
4. 開催地が同じ距離にあるとき、Records_APIは一貫した順序を維持すること

### 要件6: パフォーマンス要件

**ユーザーストーリー:** ユーザーとして、検索結果が素早く表示されることを望む。そうすれば、待つことなく開催地を見つけられる。

#### 受け入れ基準

1. 開催地を検索するとき、Records_APIはリクエストの95%に対して500ms以内に応答すること
2. GeoHashインデックスが使用されるとき、データベースクエリは前方一致検索にインデックスを使用すること
3. 9ブロック検索を実行するとき、Records_APIは各ブロックの検索を並列実行すること
4. 複数回の反復が必要なとき、Records_APIは最大反復回数を5回に制限すること
5. 検索がタイムアウトしたとき、Records_APIは利用可能な最良の結果を返却すること

### 要件7: エラーハンドリング

**ユーザーストーリー:** 開発者として、システムがエッジケースを適切に処理することを望む。そうすれば、アプリは安定したままになる。

#### 受け入れ基準

1. 位置情報パラメータが無効なとき、Records_APIは説明的なメッセージとともに400エラーを返却すること
2. 開催地が見つからなかったとき、Records_APIは200ステータスで空の配列を返却すること
3. GeoHash計算が失敗したとき、Records_APIはエラーをログに記録し500エラーを返却すること
4. データベースクエリが失敗したとき、Records_APIはエラーを返す前に1回リトライすること

### 要件8: API仕様

**ユーザーストーリー:** モバイル開発者として、明確なAPI契約を望む。そうすれば、検索機能を正しく統合できる。

#### 受け入れ基準

1. Records_APIは`GET /venues/nearby`エンドポイントを提供すること
2. エンドポイントを呼び出すとき、アプリは`latitude`、`longitude`、`limit`クエリパラメータを提供すること
3. リクエストが成功したとき、Records_APIは`id`、`name`、`location`、`distance`、その他の開催地プロパティを含むJSON配列を返却すること
4. リクエストが失敗したとき、Records_APIは`error`と`message`フィールドを含むJSONエラーオブジェクトを返却すること

### 要件9: GeoHash精度設定

**ユーザーストーリー:** システムアーキテクトとして、設定可能なGeoHash精度を望む。そうすれば、異なるユースケースに最適化できる。

#### 受け入れ基準

1. DynamoDB_Clientは開催地を保存するとき、GeoHashを8文字（±19m）の精度で計算してシャドウインデックスに保存すること
2. Records_APIは検索するとき、デフォルトのGeoHash精度として6文字（±610m）を使用すること
3. 検索するとき、Records_APIは精度6から開始し、必要に応じて精度4まで緩和すること
4. 最小精度（4文字）に達したとき、Records_APIはそれ以上緩和しないこと
5. Records_APIは環境変数を介してシャドウインデックス精度（GEOHASH_SHADOW_PRECISION）と検索開始精度（GEOHASH_SEARCH_PRECISION）の設定を許可すること
6. シャドウインデックス精度が検索開始精度より高いとき、将来的に検索精度を上げる際にデータ再計算が不要であること
