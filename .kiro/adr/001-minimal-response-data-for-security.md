# ADR 001: 最小限のレスポンスデータ（セキュリティ重視）

## ステータス

採用済み

## 日付

2026-01-09

## コンテキスト

### 発見された問題

`updateOne`操作の実装において、セキュリティ上の重大な脆弱性が発見されました：

1. **現在の実装**:
   - `updateMany`を実行（update権限でチェック）
   - その後、`findOne`を実行してレスポンスを作成
   - `findOne`は権限チェックを行わない

2. **セキュリティリスク**:
   - update権限のみを持つユーザーが、read権限なしでデータを読み取れる
   - 情報漏洩の可能性

3. **パフォーマンス問題**:
   - 更新後に追加のクエリ（findOne）を実行
   - 不要なデータベースアクセス

### 検討した選択肢

#### 案1: 最小限の情報（セキュリティ重視）

**レスポンス仕様**:
- `insertOne`: 作成したデータ全体
- `updateOne`: `{ id, ...更新したフィールドのみ }`
- `deleteOne`: `{ id }` のみ
- バルク操作: IDのみ

**メリット**:
- セキュリティ: read権限なしで情報漏洩しない
- パフォーマンス: findOneの追加クエリ不要
- 整合性: 全操作で最小限の情報のみ返す統一ポリシー

**デメリット**:
- クライアントが完全なデータを必要とする場合、追加のfindOneが必要

#### 案2: 完全な情報（利便性重視）

**レスポンス仕様**:
- 全操作: 完全なレコードを返す
- バルク操作: `items`フィールドで完全なデータ

**メリット**:
- クライアントの利便性が高い
- 追加のクエリ不要

**デメリット**:
- セキュリティリスク: update権限のみでread権限がない場合に情報漏洩
- パフォーマンス: updateOneで追加のfindOneクエリが必要

#### 案3: 条件分岐（複雑性）

**レスポンス仕様**:
- read権限がある場合: 完全なデータ
- read権限がない場合: 最小限のデータ

**メリット**:
- セキュリティとユーザビリティの両立

**デメリット**:
- 実装の複雑性が高い
- レスポンス形式が権限によって変わる（予測困難）
- テストが複雑

## 決定

**案1: 最小限の情報（セキュリティ重視）を採用**

### 具体的な仕様

```typescript
// insertOne
{
  id: 'user-123',
  name: 'John Doe',
  email: 'john@example.com',
  createdAt: '2026-01-09T00:00:00Z',
  updatedAt: '2026-01-09T00:00:00Z'
  // 作成したデータ全体
}

// updateOne
{
  id: 'user-123',
  name: 'Jane Doe',
  status: 'active'
  // 更新したフィールドのみ（email, createdAt等は含まれない）
}

// deleteOne
{
  id: 'user-123'
  // IDのみ
}

// バルク操作（insertMany, updateMany, deleteMany）
{
  count: 2,
  successIds: { 0: 'id-1', 2: 'id-3' },
  failedIds: { 1: 'id-2' },
  errors: { 1: { id: 'id-2', code: 'ERROR', message: '...' } }
  // IDのみ（現状維持）
}
```

## 理由

### 1. セキュリティ最優先

権限分離の原則に従い、update権限とread権限を明確に分離します。update権限のみを持つユーザーが、read権限なしでデータを読み取れる状況は、セキュリティ上許容できません。

### 2. パフォーマンス向上

`updateOne`で追加の`findOne`クエリが不要になり、データベースアクセスが削減されます。

### 3. 整合性

全操作で「必要最小限の情報のみを返す」という統一されたポリシーを適用します。

### 4. 明確性

クライアントは「何が更新されたか」を正確に把握できます。レスポンスに含まれるフィールドは、実際に更新されたフィールドのみです。

## 影響

### 実装への影響

1. **updateOne.ts**:
   - `findOne`の呼び出しを削除
   - `updateMany`の結果から、更新したフィールドのみを抽出して返す

2. **型定義（types.ts）**:
   - `UpdateOneResult`の型定義を更新（必要に応じて）

3. **テスト**:
   - `updateOne`のテストを更新
   - レスポンスが更新したフィールドのみを含むことを検証

### クライアントへの影響

1. **破壊的変更**:
   - `updateOne`のレスポンスが変更される
   - 完全なデータを期待しているクライアントは修正が必要

2. **移行パス**:
   - クライアントが完全なデータを必要とする場合:
     ```typescript
     // Before
     const updated = await updateOne({ id, data });
     // updated には完全なデータが含まれる
     
     // After
     const updated = await updateOne({ id, data });
     // updated には id と更新したフィールドのみ
     
     // 完全なデータが必要な場合は追加のfindOneを実行
     const full = await findOne({ id });
     ```

3. **react-admin統合**:
   - `dataProvider`の`update`メソッドを更新
   - 必要に応じて追加の`getOne`呼び出しを実装

## 代替案の却下理由

### 案2（完全な情報）を却下

セキュリティリスクが許容できないため却下。update権限のみでread権限がない場合の情報漏洩は、重大なセキュリティ脆弱性です。

### 案3（条件分岐）を却下

実装の複雑性が高く、レスポンス形式が権限によって変わることで、クライアント側の実装が複雑になります。また、テストケースが増加し、保守性が低下します。

## 備考

この決定は、セキュリティを最優先する設計思想に基づいています。将来的に、クライアントの利便性を向上させる必要がある場合は、以下のオプションを検討できます：

1. **オプションフラグ**: `{ includeFullData: true }` のようなオプションを追加（ただし、read権限チェックが必須）
2. **GraphQL**: より柔軟なデータ取得が可能なGraphQL APIの導入
3. **バッチAPI**: 複数の操作を1回のリクエストで実行できるバッチAPIの導入

ただし、これらのオプションを実装する場合でも、セキュリティを損なわないよう、適切な権限チェックを実装する必要があります。
